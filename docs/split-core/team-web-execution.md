# Bitbid hosted team application execution contract

Status: architecture and product/security choices agreed on 2026-11-09, amended by the accepted [production authentication and D1 hosting decision](production-web-auth-hosting.md) and [blockchain authority/synchronization contract](blockchain-authority-sync.md) on 2026-11-11. Canonical decision: [Rebase the SSR execution decision on the shipped Yew and shared core](https://github.com/igmrrf/bitbid/issues/27). This records accepted Q1–Q12 and the implementation gates that follow; it does not claim a hosted product exists.

## Accepted destination

Bitbid has a public landing page and an authenticated application for teams. Sign-in lands a user on a team dashboard. Owners and Admins manage team secrets; Members receive explicit vault-scoped access. One account can belong to multiple teams. The roadmap includes usable secret management, not merely a dashboard illustration.

Keep Yew and an Axum-compatible backend on the selected Cloudflare Workers Paid runtime, with D1 managed SQLite for bounded projections and private optional web state. The accepted production decision supersedes this contract’s former PostgreSQL/managed-identity-provider requirements and its prospective database-authoritative account/team/role model. Neon and Hyperdrive are unselected. Canonical wallet/account, team, role, relationship and current authority belong on-chain under [Define blockchain-authoritative teams and standalone client synchronization](https://github.com/igmrrf/bitbid/issues/57); this does not claim the existing registry already supports teams. Render the landing page and non-secret dashboard frame on the server; unlock/decrypt vault contents in the client. Reuse the shared core where its contracts fit. A framework change to Leptos is not required. Native CLI distribution proceeds independently under the publication contract.

## Identity, membership and key access are distinct

- Use self-owned optional web authentication with established Rust libraries: wallet-only sessions, optional email/password and optional Google/GitHub relying-party links to the canonical wallet. All privileged web sessions/actions, including wallet-only Owner/Admin actions, require server-verified TOTP MFA; a browser flag or provider profile field is not evidence. Full standalone CLI/chain access remains independent of web login/MFA. The accepted origin is `https://bitbid.theldo.com`; actual runtime, OAuth registration, DNS, mail and delivery qualification remain deployment prerequisites.
- Canonical identity and invitation/role authority follow the accepted [blockchain-authority contract](blockchain-authority-sync.md). Optional Google links use validated issuer+subject; GitHub links use its authenticated-user API ID. Wallet/provider linking requires fresh selected-wallet proof plus authenticated proof of the intended existing identity; matching email, a self-signature or a profile field cannot merge accounts. Use its separately qualified bounded EOA wallet+protocol-key proof profile; first binding proves both, wallet rebinding requires old/new wallet approval plus the current protocol key. Contract wallets/guardians are separate unselected scope. Directory-key updates cannot replace per-team roster keys or grants.
- Owner manages ownership transfer, team deletion and privileged roles. Admin manages ordinary membership and team secrets. Members see only assigned vaults; grants distinguish reading from modifying secrets, with read-only as the initial grant default.
- Owners/Admins receive access to all team vaults. Role assignment alone cannot invent decryption keys: an authorized unlocked client must supply cryptographic grants. Promotion/invitation remains pending until the required key delivery is complete. The accepted qualified key-protocol contract fixes authenticated recipient-key binding and exact all-vault grant/acceptance changes; implementation remains gated.
- Every server query/mutation resolves the actor from its validated session and checks canonical membership, role and requested vault access under the approved accepted-head/finality/revalidation rule; a database projection cannot invent current chain rights. A request's team ID, role or user ID is not trusted authority. Cross-team ID substitution and direct endpoint calls must fail. Qualified v1 starts with exactly one Owner and has transfer, not add-Owner or guardian reset; preserve that Owner invariant unless the authorized terminal team deletion is executed.

## Client custody and recovery

The host stores ciphertext and never receives the vault passphrase, recovery key, vault decryption keys or decrypted secret names/values. Vault unlock is separate from sign-in. Web-account recovery restores only web-login access. A saved recovery code plus its encrypted account wrapper can restore the same protocol root/identity; the separate EOA wallet needs its own backup. Fresh protocol-key replacement requires reverified per-team roster/grant changes and affected-vault rotation; an authorized unlocked Owner/Admin can regrant only permitted current epochs. Loss of the last Owner root and recovery material may permanently block ownership actions even when its wallet survives. The operator has no recovery master key. Losing every authorized key and recovery key can make data irrecoverable.

Secret names, values and vault labels are encrypted. The server may retain account/team membership, opaque vault/item IDs, permissions, timestamps and ciphertext lengths. Search over encrypted names/values runs in the unlocked client. Audit events contain actor/action/opaque target/time, not plaintext labels, values, tokens or key material.

Keys and decrypted content stay in client memory while unlocked; plaintext/key storage in localStorage, IndexedDB, service-worker caches, URLs, analytics or error reports is excluded. Lock on logout/reload; an inactivity lock must clear controlled secret state. A concrete inactivity/session timeout, key ownership types and best-effort memory clearing are implementation-contract outputs, not a claim that every JavaScript/WASM/compiler copy can be erased. Client locks and server session revocation are separate mechanisms.

Pending removal immediately freezes the initiating client’s new writes/shares and may conservatively deny host routes; global canonical rights change only at accepted chain finality. Stale or unavailable chain authority fails current operations closed under the accepted chain contract; no instantaneous global revocation is promised. Saved historical/offline exports allow explicitly labelled preview only, never current publication/share/import. Key rotation and re-encryption follow the accepted key-protocol contract and its gated implementation. Revocation cannot erase plaintext or keys a previously authorized recipient already copied. A browser client also trusts delivered client code: stored-ciphertext confidentiality is not a promise to withstand malicious replacement of the client bundle, XSS or a compromised endpoint. Harden and verify the delivery path; document this threat limit accurately.

## Scope relative to earlier decisions

This explicitly supersedes the prospective **server-unlock** architecture in [SSR key handling](ssr-key-handling.md) for the new hosted team-vault product. It does not move native blockchain-signing keys to the host or change the existing CLI wallet policy. Retain the historical decision and its reasoning as provenance.

Existing browser-local seal/unseal and canonical/legacy token readers remain compatible. Preserve existing wire bytes, HKDF labels, deployed contract/address/ABI and stored wallets. The accepted [qualified team-vault contract](team-vault-keys.md) fixes the new envelope, key hierarchy, sharing, recovery and rotation; do not relabel an existing cryptographic domain or silently reinterpret legacy tokens. Hosted CLI/service-account access remains included follow-up work and is not claimed by the independent v0.1.0 native release.

Native FileStore and CLI wallet paths are not a multi-user tenancy store. The first hosted account/team dashboard need not wait for unrelated native wallet/IPFS/signing extractions; it uses D1 for bounded non-authoritative chain projections, private optional auth/session state and opaque ciphertext metadata. Database rows do not establish canonical team/role authority, and private credentials are not rebuildable chain data. Readiness now requires the selected runtime/auth and blockchain-authority gates below. Secret-management implementation waits for the key-protocol gate.

## First implementation seams and proposed locations

Current native root is still `bitsec/`; current web root is `webapp/`. Local directory relocation is a separate coordinated cutover. Keep independent lockfiles.

- `webapp/crates/server` (new, package `bitbid-server`, unpublished): qualified Workers/Axum composition, optional wallet/provider/password/MFA session verification, chain-authority revalidation, D1 persistence, request limits and SSR/static asset delivery. No native wallet-password or secret-decryption endpoint.
- `webapp/crates/app`: retain Yew; separate SSR-safe landing/dashboard frame from browser-only wallet integrations and vault state. Existing standalone crypto remains a distinct compatible flow.
- `webapp/crates/core`: keep the facade thin; shared native/WASM team-vault primitives belong in `bitbid-core` only after the separate protocol contract is reviewed. No database/HTTP/identity-provider code enters the shared pure core.
- D1 migrations define private optional credential/session/MFA/replay state, bounded chain projections, opaque ciphertext/grant metadata and redacted audit events only after the relevant contracts freeze their schemas. Canonical chain roles/relationships remain outside database authority. Fixed prepared statements, atomic conditional mutations and qualified transactional batches enforce local one-use/version invariants; zero affected guard rows deny the dependent action, even if the batch has no SQL error. Do not assume interactive Rust transactions or PostgreSQL row locks. Security reads use the direct primary binding; client bookmarks/replica reads cannot undo revocation. Tests require actual D1-compatible and separately authorized selected-target proof, not a map substituted for authorization.

Initial interface responsibilities (exact DTOs/schema frozen in each ready ticket):

- Session identity: generation-bound canonical wallet reference, validated optional provider identity and server-held MFA assurance; never browser-supplied roles or a database-only identity/role substitute.
- `/api/me`: canonical account and allowed team membership projection under the approved freshness rule, excluding provider tokens and vault keys.
- `/api/teams/{team}/dashboard`: authorized team/vault summaries and ciphertext/opaque IDs only. An authenticated but locked user sees the frame and permitted non-secret summaries, with client unlock required for encrypted labels/content.
- Team/member/vault/item mutations: server-side action/tenant checks, replay/CSRF controls as appropriate, atomic conditional/batch and optimistic-version handling and safe error projections. An API success cannot claim key delivery if the cryptographic grant is still pending.

Protected routes use secure HttpOnly session cookies in production, configured origin/redirect allowlists, HTTPS, CSRF protection for cookie-authenticated mutations and explicit rate/body/page/concurrency bounds. Provider verification, SQL queries and requests have finite deadlines. Cancel/roll back uncommitted work where possible, reconcile uncertain commit outcomes before retry, and test cancellation/commit races; shutdown drains bounded work. Vault unlock/KDF/decrypt stays client-side; the distinct server-login password KDF must pass the accepted bounded runtime qualification. Timing out a task does not prove secret erasure. Exact operational limits must be stated/tested in the server ticket before its QA pass.

No encrypted-vault feature is marked delivered using mock plaintext or a fake authorization backend.
3. Deliver team creation/switching, invitations, ownership/role management, grants and redacted audit persistence. Join and privilege changes must accommodate the approved key-delivery protocol.
4. Deliver client unlock/recovery and the usable secret-management journey: authorized list/search, create/edit/reveal/copy/delete and role/permission denials; ciphertext round trips through the actual backend/database. Existing standalone browser crypto remains exercised.
5. Implement the accepted production authentication/domain/hosting/backup contract through its bounded continuations; standalone CLI/service-account access follows its [accepted separate contract](standalone-team-access.md). Private-auth restore must disable auth, rotate an independent deployment generation and TOTP encryption key, drain old-generation traffic and require fresh canonical-wallet-proven re-enrollment. A restored database cannot reactivate old credentials/sessions/replay state or grant chain rights. Prepare deployment artifacts before requesting deployment authorization.

These stages require separately sized normal implementation tickets and native dependencies. Only stages with a locked interface/acceptance matrix are ready. Do not turn an unresolved cryptographic/provisioning choice into an implementation assumption.


The accepted chain flow uses a configured vetted/default finalized-chain provider (optional own node), not a full consensus light client; ordinary users need no node setup. Provider correctness/freshness remains explicit and must be qualified. Require a cryptographically valid history plus fresh canonical chain selection, separate authority/per-vault heads and atomic CAS. Host-independent encrypted record discovery must reach two independently retained copies including owner-controlled retention, with canonical full-wire SHA256 checked separately from the qualified CID profile.

Guide recovery+wallet backup/storage once and the first-peer ceremony, automate encryption/replication/readback, batch drafts into one visible per-vault Publish flow, and show pending/included/finalized/error/conflict status, preparatory steps and costs coherently. Ordinary publication requires no repeated manual backup chore. Safe resume reconciles nonce/receipts/disclosure before retry and explicitly rebases conflicts. No fees/verification step may be hidden or omitted for convenience. Exact actual continuation links are recorded in the [chain contract](blockchain-authority-sync.md#five-bounded-normal-continuations); auth59 needs C2+C3, foundation42 needs optional D1 C4, persistence51 needs independent publication C5, adapter62 needs C2+C3+C5 without D1, and existing human63/machine64 gates remain.
