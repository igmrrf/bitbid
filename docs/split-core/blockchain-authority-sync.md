# Accepted blockchain authority and independent synchronization contract

Status: **Q1–Q8 accepted on 2026-11-11; decision adoption only, no team registry/client feature delivered.** Resolves the source contract for [Define blockchain-authoritative teams and standalone client synchronization](https://github.com/igmrrf/bitbid/issues/57). The user selected ease of use within these security requirements. Actual issue closure, commits and continuation mappings require tracker readback; neither this document nor an open implementation issue establishes delivery.

## Authority, isolation and immutable protocol boundary

Use a **new explicitly versioned team registry with no upgrade-admin, guardian reset or operator bypass**. Its address, chain, registry version, deployment block and runtime bytecode hash identify one deployment. Future incompatible versions use a new deployment and explicit verified migration; old state remains readable. Preserve the legacy `BsecSecretRegistry` ABI/address/data and all existing native formats. No old registry is relabelled as supporting teams.

The chain selects canonical account-wallet bindings, team membership/roles, vault permissions/phase/epoch, authority state and each separate vault snapshot head. D1 holds only optional private web authentication plus a rebuildable bounded projection. The host/indexer cannot issue rights, restore old membership or invent a head. Native CLI and browser can discover and use chain/IPFS records without the Bitbid web host, D1, web login, email or web MFA. Privileged web actions retain their separate session/TOTP requirements; direct wallet transactions do not acquire a global TOTP guarantee.

The [qualified team-vault contract](team-vault-keys.md) and immutable qualification corpus remain byte-for-byte authoritative for v1 wire framing, full-wire SHA256, nested plan hashes, account IDs, generations, strict complete-message pure Ed25519, HPKE, AEAD, required reference sets, actions and typed closure. The independently owned unfinished [portable core](https://github.com/igmrrf/bitbid/issues/50) is neither resumed nor changed here. New chain binding/publication proofs belong to a **separate bounded chain profile**, qualified by C1 before its APIs or production implementation. Do not add a generic arbitrary-message/raw-signing toolkit or silently add kinds to qualified v1.

Live acceptance is conjunctive: **qualified cryptographic history and local bootstrap/trust pins AND a fresh accepted canonical finalized chain selection of that history's terminal authority and vault heads**. Neither half substitutes for the other. A wallet signature/self-signed identity does not replace first-peer fingerprint/team-genesis verification. Retain observed pins and disclosure evidence on all incidents.

## Separate identities, binding and recovery

| Identity | Meaning and constraint |
| --- | --- |
| `account_id` | Opaque nonzero protocol ID16, not an EVM address, email, D1 ID or derived wallet hash. |
| Protocol identity | Qualified `identity` record: account ID, u64 generation, X25519 public key, Ed25519 public key; `key_id = SHA256(identity)` and exact self-signature. Replacement strictly increases generation; same-root wrapper recovery preserves identity. |
| Wallet | Existing supported EOA/secp256k1 type; independent local custody and backup. No contract-wallet/ERC-1271, guardian or social recovery is implied. |
| Web login/session | Optional private host credential linked through fresh canonical wallet proof; cannot register/rebind a protocol identity or confer chain rights itself. |
| Machine principal | Separately bound account/key/wallet with immutable machine classification in this chain profile. Canonical operations restrict it to active Member/read-only explicit vault grants, never Owner/Admin, grantor or writer. No new v1 role or machine wire kind; the existing runner continuation consumes this extra registry restriction. |

First registration requires both the intended EOA wallet's proof and a proof by the exact self-verified protocol signing key. Neither proof is a server assertion. Enforce one active wallet per account and one active account per wallet in this registry; historical binding rows remain audit evidence. An attacker cannot front-run proofs to select a different wallet/account/recipient or gain powers as submitting relayer.

The bounded chain profile fixes the following semantic transcript before C1 freezes its literal ABI/type hashes/test vectors. All inputs participate in both proofs: profile/version, chain ID, registry address, purpose (`register`, `rebind-wallet`, `replace-directory-key`, `update-record-locators`), account ID, protocol generation/key ID, current binding sequence/hash, old wallet, new wallet, principal classification, immutable operation-body SHA256, nonce and deadline. Chain ID is checked unsigned256, address20, account16, key/hash/nonce32, generation/sequence/deadline checked u64; absent old state is explicit zero bytes only for registration. The operation body commits **every** locator/update field, not an unrelated claimed projection. Nonce is single-use in the account/purpose domain and deadline is checked against the inclusion block timestamp, with no overflow or reusable canceled nonce.

Wallet proofs use one frozen EIP-712 domain (`name=Bitbid Team Registry`, explicit chain-profile version, actual `chainId`, actual `verifyingContract`) and purpose-specific types containing the entire transcript. Verify the exact expected EOA, canonical signature and recovery rules. Protocol proofs use a new chain-profile domain-separated, length-framed complete-message Ed25519 transcript with the same fields; **never repurpose the v1 prefix or prehash its signed records**. C1 must publish the literal field order/widths/type strings/framing and differential negative vectors; until then no production proof encoder or registry implementation is ready. This deliberately bounded proof interface is not a generic signer.

Wallet rebinding requires **old wallet approval, new wallet approval and the currently bound protocol-key proof**, over the same operation/current binding/nonce/deadline. Lost old-wallet backup cannot be bypassed by root recovery, web password reset, host/operator or a directory write. Directory-key replacement uses current wallet plus the proposed new self-verified generation's scoped proof; it changes directory discovery only. It cannot replace any team's roster key, grant, acceptance or encrypted peer pin. Each team must independently perform qualified `replace-key`/verification, old-key loss freeze and affected-vault rotation with the correct eligible actor. A wallet-only assertion cannot decrypt or act as the lost protocol key.

Qualified v1 starts with **exactly one Owner** and has no add-Owner action. Transfer replaces the Owner under its existing action/recipient-acceptance rules. No add-owner/guardian reset is invented from the phrase “at least one Owner.” Same-root recovery uses the saved recovery code **and** encrypted recovery wrapper; wallet backups are separate. Losing the last Owner root and all valid recovery material may permanently prevent ownership actions, even if its wallet is backed up; losing the required old wallet may prevent rebinding even if its protocol root survives. Other current authorized clients may recover only data/actions they actually possess; no host escape hatch or automatic history regrant.

## Canonical public state and operation invariants

These tables freeze required state relations, not a deployed Solidity storage layout. C1 must freeze exact ABI/event/projection encodings and complete validation predicates consistent with them. No caller-supplied `is_admin`, `grants_complete`, ABI roster or opaque hash can substitute for validating its committed canonical bytes.

| Public state | Required fields and invariant |
| --- | --- |
| Registry identity | Chain ID, registry address/version, immutable code identity and deployment block; reject other deployments and unknown versions. |
| Account directory | Account ID, current generation/key ID, full self-verified identity commitment/retrieval ref, EOA/current binding sequence/hash, principal classification, consumed nonces; immutable prior binding history. |
| Account encrypted record locators | Account/generation/key ID, record kind, full-wire digest, byte length, bounded CID/profile/retrieval refs, monotonically checked locator sequence and authorization proof; independently discover identity, pass/recovery wrappers and encrypted trust state. AEAD wrapper fields are not mistaken for publicly verified plaintext. |
| Team authority | Team ID, pinned genesis full-wire digest, current authority full-wire digest, plan hash, u64 sequence, terminal deletion flag; exact canonical roster (account/key/role/status) and sorted vault policies. |
| Vault policy | Team/vault ID, u64 epoch, active or rotation-required phase, key commitment, exact sorted account permissions joined to active current roster keys; staging never canonical. |
| Separate vault head | Team/vault ID, epoch, snapshot full-wire digest/u64 sequence/previous hash, authority plan hash; authority refs are activation anchors, not overwritten on every ordinary edit. |
| Immutable records | Kind, complete-wire SHA256/length and bounded retrieval ref/profile for every required public proof and encrypted body. Identical digest never maps to different bytes; locator updates cannot alter committed bytes or skip validation. Retained refs preserve original plan/AAD/signature. |
| Publication identity | Actor account/key/current wallet, operation purpose, expected authority/head set, immutable candidate digest, scoped consumed nonce/deadline and resulting selection; identical replay returns the same result, differing payload under one nonce fails. |
| Receipt/checkpoint | Chain/registry/version/code identity, transaction hash, successful status, operation/nonce/body digest, block number/hash, transaction/log index and selected authority/head values; inclusion and accepted finalization are separate facts. |

| Operation | Required checks before atomic selection |
| --- | --- |
| Register/update directory | Exact scoped wallet+key proof, identity self-signature, uniqueness/generation/binding CAS, full committed fields, nonce/deadline; no team rights implied. Rebinding has both wallet proofs above. |
| Team genesis | Current bound creator wallet/key, unused team ID, exact signed v1 `genesis`, sequence1/zero previous hash, one active creator Owner and empty vault/grant/snapshot/acceptance sets. |
| Authority actions | Preserve the exact qualified table for `invite`, `activate`, `promote`, `demote`, `replace-key`, `remove`, `new-vault`, `vault-permission`, `rotate`, `transfer`, `delete-team`. Derive actor eligibility from **previous** active roster/current team key and its current bound wallet, never proposed privilege; apply exact unique target/diff, cardinality, permission, freeze and reference rules. |
| Ordinary vault publication | Current active read-write actor and bound wallet; CAS current authority plus this vault's current head; unchanged epoch/current plan, next snapshot sequence/previous hash, exact item-ID set/revision/kind relation and signatures. Owner/Admin only for label changes. Batch valid local draft changes into **one chain head commitment per vault publication**. |
| Authority transition/rotation | CAS old authority **and all required latest existing vault heads**, seal every prior-plan extension; apply complete roster/policy/required grant/snapshot/acceptance relations atomically. Rotation has exact item-set/kind equality, checked next revisions/epoch, fresh commitment/new refs; no partial activation, missing proof, staging rights or combined edit/rotation. |
| Removal/access loss | Exclude removed/replaced keys from new grants; freeze affected vault writes/new grants/epochs until complete authorized rotation. Read-only downgrade alone does not erase a key. Terminal deletion has no successor and does not erase history. |
| Nonce/retry | Same nonce and exact immutable body identifies one operation. Conflict/expiry/failure cannot make a different body valid under it. Rebase is an explicit new operation after current-state verification, never blind last-write-wins. |

All required public signatures/state relations are enforced **before a head can be selected**: identity self-signatures; authority actor; every required newly introduced grant, snapshot/content author and recipient acceptance; exact provenance/continuous selection/equality for retained refs; current actor rights and full required reference sets. Previously validated immutable records may be referenced only through a sound bound validation cache in this exact registry/profile; C1 proves this equivalent to full verification. Submitted bytes must parse/reconstruct exactly qualified canonical full wires, not an ABI/JSON approximation. Verify strict Ed25519 on the **complete** canonical v1 signing message, canonical public key/R encodings and small-order rejection equivalent to the qualified verifier. No assumed cheap Ed25519 precompile, Ed25519ph/prehash substitution, opaque proof bridge, trusted signer or optimistic fallback.

C1 must prove supported worst-case team/vault/record/ref/history bounds against calldata/gas/storage/atomicity on the actual selected fork. Core parser maxima (16 MiB records, 256 MiB exports, 10000-entry lists) are **not** promises that one EVM transaction can handle them. Any narrower product capacity requires an explicit reopened decision and user acceptance; no silent truncation, proof omission or capacity reduction. Qualification failure blocks actual registry and dependent production clients and reopens **On-chain complete-message public-v1 validation feasibility/capacity** under the chain decision. A valid public signature still cannot prove a malicious writer supplied decryptable ciphertext, correctly encrypted every recipient key, preserved plaintext during rotation, or retained bytes.

## Submission, disclosure and recovery state machine

Persist separate `prepared`, `uploaded`, `sent`, `possibly-disclosed`, `included`, `finalized`, `conflicted/failed` observations with immutable payload/nonce/expected-head and receipt evidence. These are operational observations, not new v1 wire kinds or rights. For grants, obtain trusted-peer verification and required pre-key acceptances first; real current-epoch grant bytes leave the client only with the signed complete activation payload, even if replication precedes chain inclusion. Once uploaded/sent, count them as possibly disclosed. An HTTP timeout, rejected transaction, cancellation or reorg never turns that into “undisclosed.”

After uncertain send, query the nonce/operation and qualified canonical finalized receipt/selected state before retry; preserve disclosure evidence and reconcile both inclusion and current selection. A finalized operation may subsequently be superseded by another valid operation, so receipt success alone does not prove it is current. Abandoned/revoked possibly disclosed grants require affected-epoch rotation. One competing authority/content CAS wins; losers reload, verify and explicitly rebase. Background retry cannot overwrite a newer head or silently re-encrypt under stale membership/epoch. Do not promise a single transaction for arbitrary record size before C1 qualification; qualified preparatory steps share one coherent visible Publish journey and disclose costs.

Local pending removal immediately stops the initiating client's new writes/shares, and a host may conservatively deny its own routes. Global canonical rights change only at accepted finality; no instantaneous global revocation before that point. Reorg/outage suspends current operations. Preserve last accepted pins, canonical evidence, rejected bytes and grant disclosures on incidents; never force an older pin or mark invalid crypto valid to unstick a team. Remaining users can preview readable historical recovery. If selected current history cannot be used, an explicit **new-team/genesis migration** with new team ID/keys, verified current recipients and new grants may import locally recovered data as new records; it is not continuation/reset of the old team. Missing records, roots or recovery material can make recovery impossible. Historical keys/public ciphertext cannot be recalled or erased.

## Finalized observations and rebuildable D1

V1 trusts the **configured approved/default node/provider** for finalized-chain information, with an optional independently operated node/provider. Provide a vetted default profile so ordinary users need not run a node. This is an explicit trust assumption: RPC responses, even mutually agreeing endpoints, do not independently prove global latest state or consensus. No full consensus light client is selected. This decision selects neither a paid provider nor a qualified endpoint; provider entitlement/cost and actual capability remain C1/C3 gates.

Resolve a qualified `finalized` block number/hash and bind related code/state/receipt reads coherently to that hash with qualified EIP-1898 canonical checks (or a separately proved equivalent profile). Verify chain ID, registry version/address and actual runtime code hash. Do not combine unrelated `latest` reads or replace missing finalized support with an invented N-confirmation delay, `safe` assumption or stale D1 row. Check receipt success, canonical inclusion and that its block is an ancestor of the accepted finalized checkpoint. Detect unsupported/pruned/history/inconsistent/lagging replies, bound retries/deadlines and expose outage/stale status. C1/C3 freeze measured freshness/staleness limits and clock policy; expired/unavailable freshness fails current operations closed.

Index from the verified deployment block through bounded complete log ranges with bounded bytes/results/retries/backoff; validate address/topics/version, canonical block hashes and deterministic `(block number, transaction index, log index)` order. Event identity includes chain/registry/block hash/transaction/log index. Duplicate replay is idempotent; a failed, truncated or timed-out range never advances the cursor as empty. Commit projection effects and cursor atomically only after complete validated batch. Store block-hash checkpoints, recheck them on resume/reconnect, rewind to the verified common ancestor for pre-finality reorg and backfill every gap. A subscription/`removed` flag alone is insufficient. Inconsistency at an accepted finalized checkpoint freezes the projection and current operations for investigation, without erasing client pins.

D1 projection rows/cursors carry deployment generation, chain/registry/version/code identity and accepted block hash/height. Rebuild into a new generation from chain/public records, validate complete replay and switch only after matching finalized selection; private auth restore still follows the separate independent-generation re-enrollment contract. Every hosted authorization requires **validated session/MFA + correct deployment generation + fresh accepted canonical membership/vault permission + valid requested scope**, with conditional mutation guards against current heads. SQL membership, restored rows or an indexer flag alone cannot authorize. Direct clients perform equivalent chain/profile/history checks without D1.

If fresh canonical state is unavailable, allow only explicitly labelled **saved historical/offline export preview** under the verified typed closure and saved pins, with its saved block/context and freshness limitation displayed. Do not enable current publication, sharing/grants, role changes or current import; recovery does not silently become current authority. Public IPFS fetch success and a cryptographically valid old export do not change this rule.

## Independent encrypted availability and smooth flow

Chain discovery must lead directly to account identity, pass/recovery wrappers, encrypted trust wrapper, team genesis/authority/acceptance history, current recipient grants, each selected snapshot and complete selected content/proof closure. Account record updates are wallet+key authorized/versioned, but wrapper ciphertext remains AEAD-verified locally. Public identities/roles/relationships/CIDs/timing are visible metadata; names/labels/values and all roots/passphrases/recovery codes remain encrypted/client-only. The host/indexer/storage provider receives neither plaintext nor unwrapping capability.

Anchor **SHA256 of complete canonical wire bytes** separately from the CID and record byte length. C1/C5 freeze a bounded fixed CID version/codec/hash/import/chunk/DAG/retrieval profile, canonical CID encoding, permitted gateway/node behavior and aggregate traversal/size/time budgets. CID is not assumed to equal reconstructed-file SHA256; do not presume enormous raw blocks work. Verify the CID/DAG path, reassembled exact bytes/length/digest, v1 signatures/context/closure and canonical current selection independently. Malformed/partial/missing bodies never become valid through an on-chain hash or gateway HTTP200.

Before activation, require **two actually independently retained encrypted copies, including one owner-controlled retention location** usable without the Bitbid host/account. Two gateways to one storage account/node are not two independent copies. Freeze responsibilities/credentials/access domains and failure assumptions; make storage/egress/gas costs visible before enabling the profile. Setup automation configures approved encrypted storage/credential handles, replicates complete closure, fetches it independently from each retained location and validates full closure/readback, including an owner-controlled host-offline restore test. Health checks/retries report lost copies; repair from a surviving verified copy, preserve recoverable records, and fail new publication closed if the required two-copy retention cannot be established. A successful readback proves availability then, not permanence; both lost copies may be irrecoverable. Never imply that D1 backup restores missing IPFS objects.

The product must make this usable: guided **one-time** wallet-backup and protocol recovery save/test, storage/owner-retention setup and first-peer verification; background encryption/replication and finite progress; local drafts batched into one visible **Publish** per vault with clear pending/included/finalized/conflict/error states. Ordinary publications do not require manual backup chores. Present any qualified preparatory transactions, user-funded fees and retention obligations as one coherent flow; do not hide fees or promise unsupported one-transaction capacity. Resume exact immutable work after lock/crash/network failure with safe receipt reconciliation and explicit rebase on conflict. First-sharing/replacement ceremonies and accepted verification cannot be skipped for convenience.
