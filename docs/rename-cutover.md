# bitbid cutover and compatibility

The package remains `bitbid-cli` 0.1.0. Its only executable, CLI help, banner,
completion registrations and current examples use `bitbid`. Build/install from
the checked-out source using [Cargo](cargo.md); the canonical source repository
is https://github.com/igmrrf/bitbid. No canonical homepage or published npm,
Homebrew, container, OS package or downloadable binary is established here.
Those guides are prospective templates requiring separate release work.

## Owned installation upgrade

`cargo install --locked --path crates/bitbid-cli --root /path/to/owned-install --force`
installs `bin/bitbid`. Cargo may retain an earlier tracked `bsec` executable:
inspect `cargo install --list --root /path/to/owned-install`, then remove only
that old binary using
`cargo uninstall --root /path/to/owned-install --bin bsec bitbid-cli`.
Verify `bitbid --help`, `bitbid --version` and `bitbid completion bash` through
the same root. Do not globally uninstall, remove unrelated commands, or assume
`--force` itself removes stale binary ownership. There is no `bsec` command alias.
Reinstall shell completions generated by `bitbid completion <shell>`.

## Runtime aliases through 0.x

`BITBID_HOME` and `BITBID_PINATA_JWT` win by presence, including blank or invalid
values; their `BSEC_HOME` / `BSEC_PINATA_JWT` aliases are considered only when
the canonical environment variable is absent. Blank selected HOME fails safely;
blank selected JWT disables that env source. Nonblank `ipfs.pinning_jwt` config
still wins before either env name. Invalid selected credentials fail before auth.

With no explicit HOME override, existing `~/.bitbid` wins; if absent, existing
`~/.bsec` is used in place; if neither exists, `~/.bitbid` is created privately.
Invalid selected paths fail, with no legacy fallback. Wallet, network config,
index and cache use the same selected root. Cwd `.bitbid.json` wins over
`.bsec.json`; malformed/unreadable selected config fails even with explicit flags.
Explicit saves use the selected file in place; no automatic copy, merge, move,
delete or data migration occurs. Valid CLI flags override valid config fields.

Each selected legacy surface emits its fixed redacted deprecation warning once
per process. Legacy env/path/type aliases remain supported through 0.x and are
scheduled for removal at 1.0. `BsecError` remains a Rust type alias of
`BitbidError`; error kinds, exit codes, token formats and persisted schemas stay
compatible. See [execution contract](split-core/rename-execution.md) for exact
selection, error and warning bytes.

Test-only switches are exclusively `BITBID_E2E`, `BITBID_E2E_RPC`,
`BITBID_E2E_REGISTRY`, `BITBID_E2E_IPFS_GATEWAY`, `BITBID_E2E_FUNDER`.
They have no old-name aliases and are not deployment settings. Default offline
suites and synthetic RPC probes do not prove live chain/IPFS or hosted CI.
Actual local encrypted settings gates are `make secrets-catalog-check secrets-report`;
the checked-in catalog is unset-only and enables no optional Pinata auth.

## Remaining old-name classification

- Wire/cryptography/chain identity: `bsec-ecdh-aes256gcm-v1` HKDF context,
  `BsecSecretRegistry` Solidity/ABI name and fixture vectors/address material.
  Changing these would break existing tokens/contracts and is outside cutover.
- Compatibility: the four legacy env/path inputs, `BsecError`, exact warning
  strings, compatibility tests, encrypted legacy-name catalog entries, and
  synthetic legacy-root fixtures. These are intentional current references.
- Existing local Compose project/container names `bsec-testnet`,
  `bsec-local-testnet`, `bsec-local-ipfs` retain resource identity so the rename
  does not strand running containers or their IPFS volume. CLI commands are canonical.
- Historical records: `CHANGELOG.md`, `PRD.md`, `docs/security_audit.md`,
  `docs/from-scratch-guide/`, `docs/research/`, `docs/superpowers/`, excluded
  `prototype/split-core-skeleton/`, dated split validation and rename/execution
  decisions preserve original observations and planned transitions. Historical
  commands are not current installation instructions. Current split protocol and
  verification guides use `bitbid`; old cryptographic labels stay intact.

## Scoped rollback and local delivery

Rollback only the coordinated N5 CI/test/helper/docs/metadata changes and local
wrapper switch together. N3 binary identity and N4 runtime compatibility are
separate reviewed deltas; restore only the intended owned delta if required.
For an owned install, retain its pre-upgrade binary/Cargo metadata snapshot and
restore those together, preserving unrelated executables. No user data migration
needs reversal. Never reset repositories or delete user homes/configuration.

Local verification covers release builds, owned fresh/upgrade installs, native
and WASM consumers, synthetic/offline journeys and the optimized browser bundle.
It does not publish releases, deploy contracts/services, use live providers or
claim remote CI success. Future publication needs separate authorization and
verified resources. The canonical browser/CLI token paths remain shared core.
