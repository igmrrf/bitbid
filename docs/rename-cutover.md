# bitbid cutover and compatibility

The package remains `bitbid-cli` 0.1.0. Its only executable, CLI help, banner,
completion registrations and current examples use `bitbid`. Build/install from
the checked-out source using [Cargo](cargo.md); the canonical source repository
is https://github.com/igmrrf/bitbid. No canonical homepage or published npm,
Homebrew, container, OS package or downloadable binary is established here.
Those guides are prospective templates requiring separate release work.

## Owned installation upgrade

`cargo install --locked --path crates/bitbid-cli --root /path/to/owned-install --force`
installs `bin/bitbid`. Cargo may retain an earlier tracked `bsec` executable:
inspect `cargo install --list --root /path/to/owned-install`, then remove only
that old binary using
`cargo uninstall --root /path/to/owned-install --bin bsec bitbid-cli`.
Verify `bitbid --help`, `bitbid --version` and `bitbid completion bash` through
the same root. Do not globally uninstall, remove unrelated commands, or assume
`--force` itself removes stale binary ownership. There is no `bsec` command alias.
Reinstall shell completions generated by `bitbid completion <shell>`.

## Canonical runtime inputs now

The four automatic BitSec fallbacks are removed at the current 0.1.0 version,
without a major-version gate. `BSEC_HOME`, `BSEC_PINATA_JWT`, `~/.bsec`, and
`.bsec.json` are ignored, including when canonical inputs are absent or invalid.
No retired-input warning is emitted.

`BITBID_HOME` alone overrides the application root. Its presence, including
blank/non-Unicode/unusable values, prevents default selection; invalid values
fail safely. Without it, `~/.bitbid` is selected and created privately when
absent. Wallet, network config, index and cache share that lazy, cached root.
An unusable canonical root fails closed. Existing valid symlinks retain their
existing behavior; dangling links fail without selecting old data.

Nonblank `ipfs.pinning_jwt` config wins before `BITBID_PINATA_JWT`. A present
blank canonical JWT disables the environment source; absent or blank config
with no canonical JWT disables Pinata. Invalid selected credentials fail before
any request. Retired JWT variables never supply credentials.

Only cwd `.bitbid.json` is loaded or explicitly saved. Malformed/unreadable
canonical config fails even with explicit flags; valid CLI flags override valid
config fields. Saves retain the existing identity/replacement checks. Old files
and directories are never automatically copied, merged, moved, deleted, rewritten,
chmodded or reencrypted.

`BsecError` remains a Rust type alias of `BitbidError`; error kinds, exit codes,
wallet schemas, canonical/legacy token readers, cryptographic labels and on-chain
formats remain compatible. This immediate four-input cutover supersedes the old
0.x/1.0 promises in the dated [execution contract](split-core/rename-execution.md).

## Explicit migration and rollback

First stop processes using either root. Privately back up both roots and project
files, recording permissions and which copy is authoritative. Explicitly choose
`BITBID_HOME=/absolute/path/to/chosen-root` to keep using an existing directory,
or copy selected files into a private `~/.bitbid` yourself after checking for
conflicts. Set `BITBID_PINATA_JWT` through your existing secure credential workflow
or retain the supported nonblank config credential. Create `.bitbid.json` from
the selected project config only after reviewing any existing canonical file.
Do not print credentials or overwrite/merge conflicting wallets or indexes.
Verify the selected wallet/config with the new binary before resuming writes.
The program performs none of these migration steps for you.

For rollback, retain the previous executable and its explicit environment/config
selection plus the private data backup. Restore only the intended source/binary
revision; stop writers before deliberately restoring any data. An older executable
can honor retired names again, so verify its selected root explicitly. This ticket
changes no data, and source rollback itself requires no data reversal.

Test-only switches are exclusively `BITBID_E2E`, `BITBID_E2E_RPC`,
`BITBID_E2E_REGISTRY`, `BITBID_E2E_IPFS_GATEWAY`, `BITBID_E2E_FUNDER`.
They have no old-name aliases and are not deployment settings. Default offline
suites and synthetic RPC probes do not prove live chain/IPFS or hosted CI.
Actual local encrypted settings gates are `make secrets-catalog-check secrets-report`;
the checked-in catalog is unset-only and enables no optional Pinata auth.

## Remaining old-name classification

- Wire/cryptography/chain identity: `bsec-ecdh-aes256gcm-v1` HKDF context,
  `BsecSecretRegistry` Solidity/ABI name and fixture vectors/address material.
  Changing these would break existing tokens/contracts and is outside cutover.
- Retired inputs: the four former env/path fallbacks survive only in negative
  fixtures, migration notes and preserved encrypted catalog inventory. Runtime
  code does not consume them. `BsecError` remains a supported Rust type alias.
- Existing local Compose project/container names `bsec-testnet`,
  `bsec-local-testnet`, `bsec-local-ipfs` retain resource identity so the rename
  does not strand running containers or their IPFS volume. CLI commands are canonical.
- Historical records: `CHANGELOG.md`, `PRD.md`, `docs/security_audit.md`,
  `docs/from-scratch-guide/`, `docs/research/`, `docs/superpowers/`, excluded
  `prototype/split-core-skeleton/`, dated split validation and rename/execution
  decisions preserve original observations and planned transitions. Historical
  commands are not current installation instructions. Current split protocol and
  verification guides use `bitbid`; old cryptographic labels stay intact.

## Scoped rollback and local delivery

For an owned install, retain its pre-upgrade binary/Cargo metadata snapshot and
restore those together, preserving unrelated executables. Follow the explicit
selection and data precautions above. Never reset repositories or delete user
homes/configuration. Push, publication and deployment require separate authority.

Local verification covers release builds, owned fresh/upgrade installs, native
and WASM consumers, synthetic/offline journeys and the optimized browser bundle.
It does not publish releases, deploy contracts/services, use live providers or
claim remote CI success. Future publication needs separate authorization and
verified resources. The canonical browser/CLI token paths remain shared core.
